# ADR-008: explicit workspace-local draft checkpoints

Status: selected for manual checkpoint/recovery; automatic timing, shutdown flushing and Windows acceptance remain open.

Add a separate `.astelvo-recovery.json` file beside the portable manifest. Its independent format is `astelvo-draft-checkpoint`, version 1, bound to the workspace ID. It is recovery data, never authoritative script/folder/classification metadata. No portable manifest migration occurs. Export/fresh-folder restore still carry saved workspace state only and omit checkpoints.

A checkpoint contains 1–16 dirty or externally reviewed editor tabs: the last reviewed saved document (including exact base source/hash and classification), draft source, name/language/folder and tag/favourite input text. Incomplete names/tag input are retained within UI bounds rather than normalized or rejected as committed metadata. Both base and draft sources retain the 256 KiB UTF-8 bound. The base hash must match its retained content. Total serialized storage and typed response size are bounded to 3 MiB, below the 4 MiB protocol frame. Many maximum-sized/escaped tabs may exceed this aggregate budget; rejection preserves the prior checkpoint and every live editor draft.

The existing workspace writer lease and managed-path/symlink checks apply. Read/write/clear use fixed host-owned paths through narrow bridge methods. Writes validate the whole candidate before staging, compare an expected SHA-256 token of the previous raw file (null means absent), then use flushed same-directory atomic replacement. Clear compares the same token and deletes only that fixed file. Manifest/source files and workspace revision do not change. These are optimistic checks against ordinary changes, not a hostile-filesystem transaction or script security sandbox.

Unknown/missing/duplicate fields, unsupported versions, bad identities, base hashes, classification or encoding fail closed. Small invalid files return their raw token and an explicit problem without exposing a snapshot; this permits reviewed discard. Linked or over-3-MiB files fail without replacement. An oversized file must be moved aside manually before checkpointing can resume; ordinary editing stays available. Temporary files left by process death are ignored and preserved. Acknowledged writes are file-flushed; no power-loss durability claim is made. Death during replacement must expose either complete generation, never partial JSON at the checkpoint path.

The renderer reads availability on workspace open/restore, but never automatically applies or consumes a checkpoint. Draft recovery offers explicit Read, Checkpoint/Replace, Recover and Discard controls. Replacement is explicitly labelled when an old checkpoint exists. Discard uses a native confirmation that distinguishes the checkpoint from live drafts and saved scripts. Saving, closing tabs/workspaces, quitting or recovery itself does not consume this deliberate checkpoint; it remains until explicitly replaced/discarded. Later edits require another checkpoint.

Recovery preflights every saved identity/source read before replacing any models. Deleted/unavailable scripts require organizer restore before retrying the whole checkpoint; partial acceptance is not performed. Existing dirty tabs require discard consent first. Recovered tabs retain their original base hashes, so stale-source saves still reject without discarding drafts or overwriting external bytes. Source/metadata/classification still require ordinary explicit Save commands. Recovered content is data and is never executed. Current checkpoint contents are those last read; reread before reviewing externally changed recovery files.

Undo stacks, selection/scroll, active-tab identity and clean tabs are outside this snapshot. Tab undo history begins anew after recovery. This batch establishes durable, explicit checkpoints and recovery, not timed autosave or an automatic shutdown journal. Full app/OS power-loss, Windows/package/clean-machine and final product acceptance remain separate gates. Renderer isolation does not sandbox future scripts, which run with user OS permissions.
